## SDK 与本机能力

本机 `D:/esp-idf/v6.1.1/esp-idf` 的 `idf.py --version` 为 ESP-IDF v6.1.1，提交 `051e4c4eb20346e043cdd47bc388fde75ff8af63`。激活环境后依赖检查和 C5 构建通过。`esp_wifi.h` 明确 band-mode API 要在 Wi-Fi started 后调用；第一次真机启动暴露了前置调用错误，已按该前置条件修复。`esp_wifi_sta_get_negotiated_phymode` 可检查 HE20。

本机 `components/app_update/esp_ota_ops.c` 的 `esp_ota_resume` 支持顺序擦写恢复，拒绝写运行槽或在未确认启动期间覆盖回滚槽。恢复检查点必须按扇区对齐，本工程用 16 KiB。IDF QEMU 配置没有 C5 机器目标，不能使用 C3 或 S3 模拟结果证明 C5 GPIO 与射频。

| 论文 | 作者提出的机制 | 本工程决定 |
|---|---|---|
| Predicting Wireless Channel Quality by means of Moving Averages and Regression Models，2306.08634v1，2023-06-14 | 比较移动平均和回归，在其 Wi-Fi 数据中 EMA 具有较低计算和存储成本 | 自动采样完成后优先实验整数 EMA；当前代码尚未实现 EMA，不声称已有收益 |

| On-Device LLM for Context-Aware Wi-Fi Roaming，2505.04174v2，2025-05-20 更新 | 以应用层上下文选择 BSSID 和动态阈值，并使用量化与微调 | 无 PSRAM C5 不具备已验证资源预算，暂不移植 |

论文中的改善数值不能成为本项目的吞吐或延迟承诺。当前实现采用双方最差链路评分、最少样本数、5 秒新鲜度、10 分滞回、30 秒驻留、15 秒回退。完整自动控制还需要双方试探测量、失败注入和第二块 C5；仅扫描 RSSI 不足以估计候选 RTT/丢包。

## OpenOCD 与 USB 方向

官方 OpenOCD `src/jtag/drivers/cmsis_dap_tcp.c`：`https://github.com/openocd-org/openocd/blob/master/src/jtag/drivers/cmsis_dap_tcp.c`。报文是小端 `DAP` 签名、u16 长度、请求类型 1/响应类型 2、保留字节；头长 8，最大负载 1024，默认 TCP 4441。源码注明 UART/SWO 未支持。后端存在不意味着所有 DAP 命令或目标调试已经互操作。

本机 OpenOCD `v0.12.0-esp32-20260831` 经 TCP relay 调用固定 Arm 命令解析器完成初始化，收到 18 条命令并以 exit 0 结束。GPIO 是测试桩，不代表 C5 无线或外部 target 调试。该 Windows 构建在检查空 socket 时重复打印 WSA 10035；记录为已观察的上游后端问题，不能宣称 OpenOCD transport 干净通过。pyOCD 适配源码与标准库分帧测试已存在；忽略目录中的 pyOCD 0.46.1 已通过真实插件列举和本地 CMSIS-DAP responder open 检查，仍未执行真实 C5 探针发现或 GDB server。

GitHub 官方仓库 API 核对：

| 项目 | 方向和许可证 | 接入意义 |
|---|---|---|
| `vadimgrn/usbip-win2`，最近 push 2026-11-22 | Windows USB/IP 客户端，BSD-2-Clause | 是将远端 USB 模型枚举到 Windows 的客户端候选，需驱动和真实枚举验证 |
| `dorssel/usbipd-win`，最近 push 2026-11-23 | 分享本机物理 USB 的服务端，GPL-3.0 | 不能替代 Windows 虚拟 USB 客户端 |

本机未发现可用 USB/IP/VHCI 服务。未经驱动枚举证据，普通 TCP DAP 代理不能标成虚拟 USB。CMSIS-DAP bulk、CDC 串口、SPI/I2C 厂商协议应分别定义设备描述符、事务长度、独占权、拔插和异常恢复；SPI/I2C 没有可直接套用的通用 USB 类。

## C5 AP 信道约束

ESP-IDF v6.1.1 的 ESP32-C5 Wi-Fi 概览说明：AP-only、STA-only 与 AP/STA 共存模式均可用；AP/STA 共存时只有一个 home channel，STA 的信道优先，AP 会通过 CSA 跟随。官方 API 说明 AP 信道可经 `esp_wifi_set_channel()` 切换，并可通知已关联站点迁移。

因此 `provision.py --ap` 使用 `WIFI_MODE_AP`，把该 C5 作为独立管理网络，不冒充 APSTA 双射频回程。2026-11-27 的 COM7/COM8 本机关联结果（信道 6、20 MHz、STA 获得 `192.168.4.2`）记录在 [固件验收记录](../../firmware/probe-c5/docs/validation.md)，仅证明两种单一角色镜像之间的 HE20 链路。APSTA 同机共存、Gateway 双设备切频、断线恢复和客户端漫游仍未验证。
