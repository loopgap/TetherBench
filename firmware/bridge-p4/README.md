# ESP32-P4 USB bridge

This is the independent P4 route: COM9 is reserved for full-speed USB and COM10 for the board's high-speed USB path. The current firmware exposes a bounded CDC framing endpoint so host tooling can validate framing before the board profile is identified. A later board profile will bind the same frame queue to a TinyUSB vendor bulk interface and the C5 transport.

The 32-byte little-endian frame is fixed-size: version (1), opcode (1), sequence (2), payload length (2), payload (24), and CRC-16/IBM (2). Payload lengths above 24, invalid versions, bad CRC, and queue exhaustion fail closed. PING is the only operation answered without a C5 link. DAP requests remain offline until an identified P4 board has a verified C5 SPI/SDIO wiring profile.

ESP-IDF 6.1.1 follows the official `espressif/esp_tinyusb` `^2.0.1~1` component range. Build with `tools/build.ps1` after activating the local IDF environment; generated build output stays ignored. The default `-UsbPort high` selects the ESP32-P4 High-Speed peripheral; use `-UsbPort full` for a separate Full-Speed image. `esp_tinyusb` installs one device stack per image, so these profiles are tested sequentially rather than advertised as simultaneous dual-port service. The CDC endpoint is a framing and smoke-test path; it is not a claim of USB High-Speed enumeration or CMSIS-DAP hardware support. Those require an identified P4 board profile and a captured USB descriptor/throughput result.

The current board is an ESP32-P4 rev 3.2 with 16 MiB flash. After replacing the factory-test image, COM10 answered the fixed-frame PING and returned `LINK_OFFLINE` for a DAP request; COM9 did not answer. Keep `WT9932P4-TINY` as a provisional board profile and do not select C5 transport pins from the GPIO count or from COM9/COM10 numbering. See [`docs/validation.md`](docs/validation.md) for the evidence and remaining hardware gates.
